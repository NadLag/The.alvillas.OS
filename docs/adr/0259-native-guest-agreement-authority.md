# 0259 — Native guest agreement authority

F-GST-07 uses the existing generated document, original PDF, signature request,
recipient, provider distribution, authenticated observation and signed archive
histories. It does not introduce another agreement renderer or signature ledger.

The `guest_hub.guest_agreement` policy requires explicit processing and wording
approval references, a processing notice, a document type and native template
family and approved immutable EN/FR/optional-AR version IDs. These are references
to actual authored templates; a later template version needs a new approval and
delegation. The native generation service continues to enforce one variant family.
It has no enabled production or approved legal default. EN and FR have
explicit selections. Arabic uses its own approved template or an explicitly
configured EN/FR fallback; otherwise that language is unavailable. The actual PDF
language and immutable template/version identity must survive recovery unchanged.

A guest request must bind the original reservation, property, canonical guest,
link and independently authorized original staff delegation. It cannot accept a
client-supplied email, document identity, signer, provider status or signed flag.
The existing native signature email distribution remains the delivery mechanism.
Provider calls require the existing policy, source, document, counterparty,
signature and transport permissions, including held and current authority.

The Guest Hub flow retains one durable guest nonce before provider I/O and recovers
an uncertain original without redistributing or generating a new PDF. Completion
requires canonical native signed evidence and both verified archived artifacts:
the signed original and its certificate. Email delivery, an unarchived completion
and a house-rules acknowledgement cannot establish agreement completion.

Prepared agreement selection has its own append-only staff release: it chooses an
actual prepared original, rather than changing a generic form flag. Its purpose-
bound signature must cover the original document/signer fingerprints and held
authorization cap. Existing form-grant signing protocols remain unchanged.

A guest delivery request records guest-capability provenance with no human staff
actor. Its native document-distribution admission must attach that provenance in
the same transaction as its outbox event. As with native identity-document
archive boundaries, a guest-origin intent cannot execute through an ordinary
document worker without the composition-supplied guest authority boundary. That
boundary rechecks the original release, processing purpose, source and held/current
staff authority at every native phase. Withdrawal before dispatch closes delivery;
an uncertain provider acknowledgement retains the original and cannot cause an
automatic second send. Canonical document/signature history remains independently
readable by authorized staff.

Staff choose an actual authorized prepared original and review their release or
withdrawal. Original requests remain independently readable after withdrawal,
processing changes or the loss of edit authority. Document version numbers used
by existing protected download links stay outside the immutable original signing
protocol. Guest JSON and PDF routes share the original scoped cookie, origin,
budget and live-authority boundaries; PDFs recheck authority after object I/O.

Source snapshots retain the existing PostgreSQL row witnesses. A logical database
restore closes the original delegation and requires an explicitly reviewed staff
release for the restored source. Original history and nonces remain retained;
recovering an earlier request cannot complete that new release. Authorized staff
can still read the original documents and signed artifacts independently.

The deferred origin check reads the inserted distribution intent's physical row
when checking same-transaction birth. The forward correction preserves the
already-applied migration and every other provenance, audit and outbox guard.

Legal wording, provider/certificate approval and restricted hosted acceptance
remain external gates. Native producer integration, delegation/history, UI and
acceptance evidence do not authorize those external decisions or production
activation. All 355 approved features remain in scope.
