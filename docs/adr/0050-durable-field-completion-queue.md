# 0050 — Durable field completion acknowledgements

DEC-12 requires Dexie and client-generated operation keys. Field completions now use an IndexedDB transaction for each enqueue and acknowledgement, with a monotonic local sequence and explicit organization/account ownership. Existing localStorage completions migrate with their original device and operation keys before the legacy queue is removed. A storage failure retains the form and reports that work has not been saved.

The server holds a tenant/device PostgreSQL transaction lock for each submitted batch. It acquires the existing task locks in stable order, then locks the performer before inserting sync records: inserting first would hold foreign-key locks that conflict with the task lifecycle's performer lock across devices. It stores the original actor, payload, client time and result; concurrent retries acknowledge that result without applying the operation again. A rejected or conflicted result stays rejected or conflicted. Reusing a key with another payload or account is rejected. A separate completion key for an already completed task returns `DUPLICATE_COMPLETION` without another completion audit or outbox event.

The browser removes work only after a recognized successful acknowledgement. Transport errors leave it queued; conflicts and rejections retain their evidence. Session ownership hints reject requests from stale tabs after an account switch. Logout and server session revocation clear local records and device metadata, while an old tab cannot erase a newly signed-in account's queue.

This queue handles the existing task-completion operation. Other operation types, the day's offline cache, cursor pull, critical stocktake resolution, photo uploads and their dependent modules retain their own acceptance requirements.
