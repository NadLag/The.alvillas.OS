# Native reservation Guest Hub capabilities

Guest Hub access is a signed capability for one canonical reservation, as required by DEC23. An issued capability includes fresh 256-bit random material, an authenticated key version and immutable original expiry. The existing private key ring supplies a purpose-separated HKDF-SHA256 signing key; HMAC-SHA256 covers the version and complete capability bytes. The key parser and existing encryption formats remain shared. Unknown versions, malformed inputs, missing private keys and cross-purpose signatures fail closed. Original verification survives deliberate key rotation while the retained key remains configured.

Public signature verification requires the selected version to contain a canonical 32-byte private key. Legacy encryption material remains readable through its unchanged encryption path; retaining it for historical decryption cannot enable a legacy-passphrase public-signature forgery.

Issuance and original-key recovery require the actual staff session, both held and current scoped authority, and independent access to the canonical reservation and guest source. Recovery belongs to the original issuer. Visitor authority grants access to that reservation through the existing authorization and presentation engines; it grants no staff, owner, financial or other-stay access. Public inputs cannot supply permissions, completion flags, tenant overrides or source values.

Expiry uses the canonical checkout calendar day, the property's actual IANA timezone and a checkout clock/grace captured from config_rule. Current eligibility and expiry are checked again using the database clock. A later checkout or longer new grace never extends the original expiry; an earlier checkout or tighter current grace can close it sooner. Revocation remains final. A changed guest or unavailable canonical source closes access. The current timezone guard is retained, including Morocco's September 2026 transition documented by [IANA](https://www.iana.org/time-zones/releases).

Business schedules, allowed reservation states and durable issuance/read budgets require explicit configuration. Processing approval has an explicit reference and no legal default. An absent approval prevents enablement. Legal/data-protection decisions and hosted/provider acceptance remain owner-reserved gates; tests use explicit owned-test configuration.

Link, original command, captured policy/source, revocation and audit history must retain tenant provenance and immutable original identities. Token material is protected by the existing purpose-bound private encryption before persistence and is excluded from audit metadata, logs and browser persistent storage. Delivery remains distinct from issuance; creating or opening a link never claims that a WhatsApp message or email was sent. Scope unchanged: all 355 approved features remain required.
