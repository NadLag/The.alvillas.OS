# 0040 — Versioned property templates and selected resets

Property, inventory, workflow, checklist and service catalog templates are immutable organization-scoped version families. An optional property scope restricts reuse to that property. Versions, applications, overrides and resets append history; database triggers reject updates/deletes and changing a family's kind/scope. Composite organization foreign keys and forced RLS protect both new tables.

Applications explicitly pin a version. Upgrades compare current values with the pinned baseline, preserve overrides, and write only newly inherited fields. Removed template fields remain on the property. Selected resets restore only the chosen pinned fields; stable item/task/checklist references preserve unrelated collection entries and ordering. Each mutation requires an expected revision, an idempotency key and a reason. Property row locks and configuration advisory locks serialize changes.

Templates orchestrate the existing property operating-profile service and configuration application service through a transactional platform bridge, preserving their authorization, validation and canonical audit events. Property details use the existing repository. They do not introduce a resolver or business-rule engine. Inventory templates configure minimums without editing stock or balances. Reservation workflow templates populate the existing task configuration; checklist references resolve through the same config engine and are snapshotted when reservations create tasks. Existing task instances and financial snapshots remain immutable. Service pricing uses Money and requires financial authorization separately from property operations.

The admin library has paginated catalogs and histories, guided bilingual editors, an explicit version selector, inheritance diffs, per-field overrides and selected resets. Archived families stay readable and pinned applications remain usable; new applications require an active family and version. Historical values and current configuration are separate views.

Audit reads and CSV exports apply the existing field serializer to service-template and service-pricing payloads. Audit access alone exposes metadata; payload values require financial view permission for the event's property scope. Stored audit history stays intact.

The configuration admin service enforces the same financial permission for service-pricing list, preview, creation, activation and retirement. Previews authorize the requested scope before resolving inherited rules. Template prices cannot bypass their access policy through the existing configuration UI.
