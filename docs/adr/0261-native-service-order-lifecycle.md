# ADR 0261 — Native service order lifecycle

Status: accepted for implementation. Required task and financial integration, provider decisions and hosted acceptance retain their existing gates.

Service orders are reservation-bound business records, with an immutable original catalog version and registered-field snapshot, a reviewed request and append-only lifecycle events. They do not create another editable catalog or financial balance. Current price, availability, quantity and reservation dimensions are reviewed before creation. Native source identities and held/current permissions are rechecked in the committing transaction.

States are REQUESTED, QUOTED, CONFIRMED, IN_PROGRESS, FULFILLED, REJECTED and CANCELLED. A CUSTOM request requires a separately reviewed quote and explicit confirmation of that recorded total. Terminal history cannot be reopened or deleted. A service date interval stays within the actual reservation; integer days and guest capacity derive from native reservation heads. The required `services.ordering` policy explicitly configures selected reservation participants, inclusive dates, quantity and duration limits without production defaults. Availability uses the existing configured public-field condition evaluator for every selected date, including interior dates. Money and registered currency precision preserve exact amounts without rounding.

Every mutation retains its original command identity, reviewed fingerprint, actor, reason, version and result. Recovery uses only the nonce and current independent source rights; a replay cannot append another event. Database constraints bind each native version and event to the same-transaction audit and metadata-only outbox receipt. Operations history is readable separately from private catalog terms, prices and financial sources.

Confirmation, task execution, collection and accounting remain distinct evidence. Confirmation creates and binds one canonical task through the existing operation service in the order transaction. IN_PROGRESS and FULFILLED require its actual native started/completed evidence, including distinct proxy validation where applicable. Forward migration262 allows a confirmed order to catch up after that actual work completes; applied migrations261/262 remain frozen. Cancellation uses the canonical task transition and cannot erase actual completed work or uncleared collections. Financial recognition through existing collection, expense, compensation and allocation services remains required under F-SVC-03. An order or quote alone never asserts collected cash, earned revenue, incurred cost or completed work. Financial allocation continues to select its configured policy at actual service completion.

The private staff interface sends account-bound same-origin POSTs under the existing session/MFA boundary. Operational lists and event identities remain separate from independently authorized original private terms. Only the command nonce may survive a hidden/offline view or interrupted response; forms, original values and reviews are cleared, and a mutation is never retried automatically. Actual reservation, catalog and checklist selectors precede server-calculated review and explicit confirmation. Original quote reasons do not enter operational task audits.
