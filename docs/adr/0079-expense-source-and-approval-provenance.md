# 0079 — Expense source and approval provenance

Date: 2026-10-26

Status: Accepted implementation decision

F-FIN-15–17 and the native expense producer required by F-AUT-03 share one expense source. Drafts use optimistic versions and audited edits. Submission facts have an append-only snapshot; later state changes preserve amounts, currency, property, reservation, purpose, funding and occurrence date. Same-tenant foreign keys and forced row security bind these facts to existing domain records.

ApprovalStage and ApprovalStageRecipient extend the existing ApprovalRequest. They retain ordered positions, configured routing, financial amounts, relevant ownership and attributed decisions. They do not replace the shared approval request, notification or ledger services. A pending stage accepts one final attributed decision with a reason; its original routing and money remain immutable.

Posting recipes reuse the existing expense allocator, owner-share allocator, Money and balanced posting assertion. Independent rounding of a shared one-cent expense previously allocated two cents. The final participating share now receives the exact remainder. Funding and beneficiary accounts remain separate, and every recipe balances in one currency.

The shared owner allocator also caps each proportional allocation at the remaining money. This prevents a negative final share when multiple tiny shares round upward and preserves the existing allocation order. Separately resolved owner expense amounts are not redistributed by ownership a second time. These changes apply to new calculations and rewrite no historical transactions.

Custom approval conditions use the existing bounded automation grammar and evaluator. Base policies and referenced values resolve from one scoped PostgreSQL read using the common configuration resolver. Unknown, unrelated legacy keys remain unparsed and unchanged. Financial occurrence dates resolve to the first instant of the property's local calendar date; skipped dates fail validation instead of selecting another day's rules.

Financial audit presentation resolves the actual expense source. It checks both current and historical amounts before exposing changes, so reducing a draft cannot reveal an earlier amount above a reader’s grant. Draft persistence creates neither a journal nor a submission event.

Submission captures the per-owner policies, exact allocation, configured recipients and calendar revenue evidence once. Concurrent original-version retries retain one snapshot, audit and native ExpenseSubmitted/ExpenseOverThreshold event. Reservation expenses require their original commission snapshots; missing historical policy or referenced values fail closed. Current agreements never substitute for missing booking history.

The existing approval form sends the current financial stage ID. A retry of an earlier decision cannot approve a later stage. Financial reads and decisions reload grants after resource locks and authorize the actual expense amount, owner and occurrence date. Notifications target only the current stage's retained recipients. Operational property approval grants confer no financial approval access. Database guards enforce source immutability, ordered recipients, stage/audience fidelity and atomic submission/event/audit records. The shared automation engine reads actual expense sources and binds its approval action to the canonical financial request.

Ordinary booking confirmation also freezes separately configured expense policies and referenced condition values in each new commission snapshot. Existing snapshots are never rewritten. Expense submission can consume the original reservation financial frame when it contains the required historical values; missing values fail closed. Requester role conditions use current scoped assignments independently from the separate permission that authorizes expense creation. They share the bounded condition evaluator.

Percentage approvals read owner-payable revenue within configured property calendar windows. The bank debit on a receipt is excluded from that revenue sum. Financial notification targets retain distinct expense and approval IDs. Channel replay checks the current retained stage and its source event; resolved owners keep access through their own retained stage.

The native property expense form, independent owner authentication, field-account denials, localized financial summary and resolved inbox history have targeted EN/FR/AR desktop/mobile acceptance with zero retries and accessibility checks. Final full integration checkpoints, required CI, financial period locks and authenticated staging remain mandatory. These features remain IN-PROGRESS.

The account-context loader now selects active assignment IDs at one authoritative PostgreSQL clock point after resource locks. The same selection feeds security enrollment and permission construction. This avoids admitting future grants or missing current grants because the application clock differs, and adds no grace period or permission fallback. Application-clock fault injection against real PostgreSQL proves both directions; the failed full-checkpoint evidence is retained.

Expense payment is a separate financial command. It requires current expense view/pay and financial transaction creation rights after the expense lock, uses the immutable submitted allocation, and waits for every configured financial approval. Account eligibility is rechecked before posting through the existing FinanceRepository. Owner charges retain their submitted per-owner amounts instead of being allocated a second time. Funding and party accounts remain distinct. The transaction uses the expense's property-local occurrence date, with that behavior stated in the localized payment form.

The existing CUSTOM expense treatment now accepts explicit per-category owner, ALVILLAS and guest shares totaling 10,000 basis points. No percentage is supplied by default. It uses the existing Money allocation and final-participant remainder, so one-cent invoices conserve their value. Submission retains the configured version and posting consumes that snapshot even after a later rule version changes the allocation. Incomplete percentages keep the expense as an editable, unposted draft.

The native draft editor reuses the existing audited update command, optimistic version, source key, authorization and creation form. Editing requires current view/edit permission independently from create permission; submitted records cannot be edited. Current selections remain stable when a funding account is unavailable or a linked reservation is beyond the first choice page. An existing financial booking link can be retained without exposing an operational reference the editor cannot view. Funding changes still require current account access, and every update retains its reason and before/after audit.

Void requires independent expense and financial-transaction void grants. It adds one journal that mirrors every original account, amount, currency, bucket and dimension with opposite sides. Its date is the current database time; the original journal link and all original postings remain unchanged. Exact retries require the original actor, reason and source version. New deferred source guards bind posted expense state to its canonical journal, original allocation and attributed audit; reversal guards require one exact mirror and atomic void state. Raw unrelated journals, unaudited void states and balanced partial reversals are rejected. Additive migrations 56 and 57 rewrite no business rows. Financial period closing/locking and privileged reopen (F-FIN-34/35) remain required dependencies before complete financial acceptance; this increment does not claim those gates.

An explicitly configured emergency exception can now bypass the owner decision only when every bypassed owner has a durable, authorized inbox receipt and an attributed audit flag in the submission transaction. The original agreement's owner routing is retained in the submission snapshot. An absent route, missing recipient or delivery failure rolls back the submission. This required financial notice survives optional operational inbox opt-outs; optional email and push still require channel consent. The existing outbox, inbox and replay keys deliver it without a separate notification engine or a fabricated approval decision.

Read-only expense viewers can receive the notice without gaining approval or posting rights. Opening the record rechecks current tenant, owner, amount and grant validity. Revocation leaves immutable notification history available but removes its record link. Recipient selection batches the existing authoritative account-context query rather than issuing one identity lookup per candidate. A PostgreSQL source guard binds each receipt to the retained owner, recipient and outbox key, and deferred guards require the receipt and audit before submission commits. Existing business rows and applied migrations are unchanged.
