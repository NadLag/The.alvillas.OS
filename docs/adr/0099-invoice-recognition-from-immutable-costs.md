# 0099 — Recognize approved invoice costs through their original line calendars

Approval state and financial recognition are separate facts. An invoice remains an immutable approved cost source; an append-only recognition header and line-to-journal links record when those costs become a supplier claim. Payment status and outstanding amounts derive from claim movements. Recognition uses the existing payable recipe and financial writer, with no physical funding account, invented expense or substitute property.

Each actual line receives a journal in its frozen cost calendar. All lines and attributed audits commit atomically under the existing canonical invoice lock. This preserves the economic date of every property and company cost when their calendars differ. The source binding and per-owner allocation conservation are validated before posting; later configuration and ownership changes do not replace submitted terms. Caller restrictions and current stored invoice, supplier, reservation and financial permissions remain independent checks before and after writes and lock waits.

Closed source dates use the existing accounting-period adjustment record and current-period override permission. That record accepts exactly one expense or invoice-recognition-line source, retaining the same actual closed period/decision, current open journal and attributed audits. A mixed invoice shifts only closed lines; open lines retain their original dates. Original expense guards and source behavior remain required regression coverage.

Recognition identity binds the complete actor and request, including the chosen date mode. Concurrent requests cannot recognize the same invoice twice. New tenant-isolated records are append-only and every line must match its actual approved submission and exact journal. Existing rows and applied SQL remain unchanged. Settlement, exact reversals, current-access readers and native acceptance remain part of F-FIN-23 before it can be DONE.

Retry results retain the original cost-position order. Generated UUID order does not define that contract: a read-only retained-data comparison found twelve recognitions whose UUID-sorted links differed from the original audited result. Replay maps immutable source lines to their existing journals and rejects an incomplete mapping; a real fifty-line regression requires the first and repeated results to agree without adding another journal.

The retained 500-line test first exposed repeated loading of a 1.17 MB immutable submission while checking individual writes. Fresh source checks now select actual source identifiers, current approval and relevant lines. Profiling then measured 32,591 queries during recognition. The existing financial repository now supports an atomic batch phase with the same Money-to-posting conversion and period guards. Its mandatory authorization callback runs before and after the actual writes; source-link writes, source audit and completed deferred guards have their own fresh checks. Sealing occurs before the final database-clock authority check. Real canonical-invoice and ledger-account waits, expiry after actual link writes and revocation after deferred guards prove rollback without a partial claim. No stored authority is cached and no assertions or timeouts change.

A versioned authorization cap serializes only the original caller's restrictions for the forthcoming durable command. It preserves sets, scope/role conditions, date limits and the distinction between missing and empty assignments. Unknown restrictions fail closed. It is never a substitute for the existing fresh stored-grant checks. Background admission, public/native command wiring and settlement remain required work before the complete feature can be accepted.
