# 0085 — Native wallet location transfers

Master specification sections 24–25, F-FIN-07/12 and handbook G.3.8 require real advances, expenses and returns in the existing employee wallet. The optional TeamWallet remains the link to the existing ledger account; no second wallet, stored balance or inventory engine is introduced. Explicit location transfers add one balanced journal. Advances move funds into linked staff wallets, returns move them back, and transfers preserve money ownership and revenue. Owner payouts retain their separate claim-changing workflow.

New transfer requests carry a normalized identity, currency, amount, purpose and reason. Existing financial authorization and independent wallet grants apply to both locations. Staff row locks cooperate with existing offboarding; current permissions are checked after period-lock waits. Exact retries retain their source actor and intent. Reversals reuse the existing immutable journal and exact-mirror constraints, with their own reasoned audit.

Forward migration 67 validates new native transfer source identities, linked active locations, movement kinds, currency precision, exact posting dimensions and attributed audits. It changes no existing business rows. The existing expense workflow accepts linked wallets with independent view/pay authority and requires wallet void authority for reversals. Existing configuration, ownership, approval, Money and audit services remain authoritative. Compensation, offsets, reconciliation and owner-payout producers retain their approved requirements and remain unfinished until independently accepted.

The new PostgreSQL lock-wait regression observes entry to the actual repository call and the actual blocked database transaction before revoking the wallet grant. It delegates to the original implementation; no posting or authorization result is replaced. Its permission, zero-write and retained-approval assertions remain unchanged.

Native acceptance also reproduced a completed wallet read being cleared by a later work-scope cursor reset. The existing cache now exposes its generation to the wallet reader. A cleared successful snapshot triggers a fresh authorized read, while an explicit financial denial clears recovery eligibility. The visible wallet follows the existing private cache subscription; late HTTP responses do not publish directly into the screen. The browser regression holds and forwards the actual PostgreSQL-backed cursor response until the first read is durable, then requires the new-generation snapshot before offline reload. No synthetic response, polling timer or weakened assertion is used.

Transfer history applies independent wallet and account read checks to both caller authority and current stored grants before presenting rows or calculating visible pagination. A general financial read grant does not disclose a separately denied staff wallet. The PostgreSQL regression reproduces both restricted caller authority and a revoked stored wallet grant, retaining authorized bank transfers beyond a full page of hidden wallet movements. No financial records or applied migration sources are rewritten.
