# Company invoice policy observations

Three actual 500-cost submissions took 4.14–4.43 seconds and issued 500 equivalent configuration reads. Repeating calendar resolution and parsing the same organization policy for each line also consumed foreground time. Every line still requires its own financial source and policy-role checks.

Company lines in one invoice now share the existing scoped configuration snapshot. The snapshot explicitly checks the transaction object, organization, normalized scope set and exact economic instant before reuse. Default callers still resolve fresh configuration; a snapshot from a completed transaction or another tenant, scope or date is rejected. The invoice operation resolves each distinct timezone's economic date once using the existing calendar helper. Rule precedence, retirement, configuration references, per-line allocation and whole-invoice approval thresholds remain in the existing engine.

The configured income-percentage case separately took 3.15 seconds to submit, with 1,000 repeated income queries. The invoice operation now observes each distinct company income basis once, after checking company-ledger authority. Its key includes the economic date, timezone, currency, period and exact configured source. Only derived window/income facts are reused inside this private invoice context. Permission decisions are not cached: financial and company-ledger checks still run for each source, and the original caller and fresh stored authority are rechecked before completion. Later operations read new configuration and income, including exact reversal movements.

After configuration and calendar reuse, the same three actual submissions take 601–694 ms and 81 client queries instead of 580. All 25 authority queries remain present. No financial journal changes during submission; actual money is still recognized separately. The configured-income case, transaction/tenant/scope/date rejection, next-operation refresh, 500 complete cost snapshots and post-read revocation have real PostgreSQL coverage. All 80 applied SQL files remain unchanged.

A separate real probe reproduced a stale related-source boundary: moving a villa to another city after the actual configuration read still disclosed its financial policy to a caller restricted to the original city. The policy fence now reuses the existing repository source read to compare current city, region, timezone, active property/supplier and reservation context before checking fresh authority. It runs before preview disclosure and after actual submission writes. A changed source denies the operation and rolls back its submission, state transitions, audits and event; a fresh operation can use the new calendar. Company-only lines retain their existing constant query count. The configured-income path now previews in 210 ms/47 queries and submits in 507 ms/83 queries, with unchanged original financial hashes.
