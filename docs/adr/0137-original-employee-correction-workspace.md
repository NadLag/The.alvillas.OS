# Original employee correction workspace

The financial workspace reviews a recognized beneficiary claim and requests its complete correction through the existing durable financial command pipeline. It displays original earned amounts separately from outstanding liability derived from postings. The operator supplies a reason and explicitly confirms the complete reversal; money, beneficiary, posting date and original journal identities cannot be edited in this flow.

The read service reuses original claim evidence, settlement preparation and correction preparation. Original salary, whole source-income exposure, all actual payment and wallet history, and opposite posting dates retain their existing held and current authorization checks. Read access can remain available while correction authority is absent. An actual payment or wallet offset must be reversed through its existing flow before the claim can be corrected. History is bounded and private to the requesting account; foreign, recognition-mode and unrelated-claim cursors are rejected.

The server renders an authenticated shell. Authorized financial evidence stays in client memory and clears during revalidation, on denied access and on connection loss. Correction controls mount only after the original recognition is authorized, allowing acknowledgements to bind the submission, claim and original recognition without a second command implementation. The existing command hook retains only a scoped random nonce in session storage. Full financial intent remains in memory for exact-body retries. Reloads recover the original request through the nonce; the existing worker remains the sole producer of correction movements.

The receipt retains typed original and opposite journal identifiers, attributed reason, posting time and immutable request history. Replacement earnings require a separate run, cost proposal and new approval. Original earnings, contracts, approvals, recognition and journal history remain retained. This UI requires no new database migration and preserves the 119-migration chain. F-FIN-24 remains in progress until complete financial and authenticated staging acceptance is met.
