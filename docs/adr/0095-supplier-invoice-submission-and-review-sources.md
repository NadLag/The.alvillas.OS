# 0095 — Retain actual supplier invoice sources in the shared approval engine

An unpaid supplier invoice is distinct from an expense already paid from a funding account. Submission must therefore preserve the invoice's actual revision and cost lines without inventing an expense, property, owner, funding location or payment.

`SupplierInvoiceSubmission` is an append-only, tenant-isolated source. It freezes the economic date, emergency request, exact original revision, complete configured allocations and routing, caller roles, whole-invoice threshold evidence, and a separate review note for each actual line. Submission takes the existing canonical invoice lock, uses an attributed version compare-and-swap, and binds retries to the actor and complete intent. A rejected invoice can create a new draft revision; earlier submissions, recipients, decisions and notes remain unchanged.

The existing financial approval service and repository accept either an expense source or an invoice submission. Invoice stages retain actual line, property and reservation identifiers and their own exact owner slice. Company costs have no property. Configured owner review stages remain present even when rounding assigns a zero-cent slice; positive-amount checks for expense stages remain intact. Review decisions, cancellation, notification resolution, source state changes and attributed audits commit in the same transaction. Caller restrictions and current stored grants are checked at the database clock before and after writes, including actual source and stage lock waits.

Owner access projects only authorized recipient stages, their line notes and allocations. It never returns the complete invoice header or another owner's rejection reason. Available stage history is paginated after authorization, and a requested stage or cursor must belong to that authorized history. Full invoice inspection continues to require independent organization-wide invoice and supplier access.

An emergency exception produces a typed, immutable notification envelope tied to an actual submission, line, owner and recipient. Its actual outbox identifier is the notice target. The existing dispatcher creates a mandatory durable inbox receipt even when optional inbox preferences are disabled. Deferred database guards require the frozen notice audience and retained receipts; the application rechecks current eligible recipients before committing. The dedicated notice reader requires that exact receipt plus caller and current source authority and returns only the addressed owner's frozen line allocation. Revocation removes the destination while preserving its history.

The shared approver selector now uses the existing authoritative identity batch and database clock. Submission rechecks every frozen approval audience in one identity batch after the actual source event write, so a source cannot commit with a required review stage whose recipients have all lost authority.

Migrations are forward-only. The original 70 migration files are preserved. The submission extension, local stage and notice guards, shared expense/invoice source guard, and notification-kind extension are separate applied migrations; none rewrites existing financial rows or applied SQL. Submission and approval create no financial transaction or supplier payment. Recognition and settlement continue to use the existing exact journal and supplier-payable kernel.
