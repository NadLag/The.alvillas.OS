# ADR 0227 — Native Management Agreement during onboarding

The Management Agreement step reuses the canonical Core agreement and its seven versioned configuration groups. It must not create another agreement model or change the Owner, Property, balances or payout accounts. The reviewed contract separates selecting an existing agreement from explicitly entering new terms.

Core supplies the shared field validation. The native input requires every financial choice, including explicit nullable end date and approval threshold, currency, approval participants, hold days, holdback, responsibilities and conditions. It must not select Core defaults or an implicit approval key. Threshold amounts remain decimal strings; integer rates remain basis points. Dates normalize to ISO instants so the original reviewed command survives JSON serialization unchanged.

Native creation must pass the actual predecessor Property, the command's single Core-compatible audit reason and explicit DRAFT lifecycle to the existing Core creation service in the same transaction. It cannot activate an agreement or a Property. Existing signed-document and legal acceptance requirements remain separate dependencies; entering terms is not legal approval.

The native source and publication boundaries must require independent current and held financial configuration authority alongside operational onboarding and Owner/Property access. Financial terms and complete original configuration values belong in authenticated encrypted history. Plaintext source witnesses contain only actual native identities, versions and tuple pins. Post-audit validation must reload authority and source state; later amendments or retirement must not replace recorded original terms.

The contract alone does not enable the shared command routes or satisfy this producer. Actual source selection, review, durable admission, immutable original history, recovery, private APIs, localized UI and complete acceptance remain required before its ordered PR can qualify.

Native review reuses financialRuleSourceChecks for every registered protected agreement group and requires its actual view/export source permissions in both held and stored authority. A financial class label and configuration permission alone cannot grant access. Actual dated rule heads support configuration conditions; undated creation requires unconditional configuration authority. Persisted source projections retain only identity/version/scope/tuple pins, while complete original dates, references, reasons and registered values require encrypted history. The generic onboarding.step_reviewed audit is reused with the actual step, and private terms stay out of audit metadata.


Bounded identities and original envelopes use the same source bridge. Batch current rule metadata for at most50 scanned canonical Agreements, authorize each candidate before loading at most20 private references, and never read financial values for a selector. Bind encrypted continuation to the actual actor cap, saved predecessor, Property source, query and policy; recheck all source/authority fences after the count-only read audit.

Share the existing Core seven-rule value constructor from its native domain rather than derive another set of financial terms. Bind the encrypted original command and complete original before/after Agreement to organization, Owner, Property, Agreement, actor, nonce, session revision and retained policy. LINK preserves original metadata; CREATE must match the actual canonical DRAFT values. Keep the existing196608-byte non-Owner envelope and all prior purpose tags. Additive225 validates native consecutive predecessors and actual same-transaction canonical DRAFT/rule/audit birth, retaining immutable history, tenant rules and future-step rejection. The application producer and its complete acceptance remain separate required work.


Native admission calls the sole Core writer in the same tenant transaction with explicit DRAFT lifecycle and explicit terms. Keep the original command, complete captured rules and selected Agreement in a purpose-bound envelope; nonce recovery remains creator-owned, while independently authorized colleagues can read history through their own held/current source grants. History reads use original version identities rather than substituting latest values and remain available under retained keys and retired policies.

Core configuration persistence applies the existing registry parser, including approval safety defaults. Validate CREATE captures against those same registered values with strict structural JSON equality: PostgreSQL JSONB object-key ordering is not a change in a financial value. Preserve the actual captured JSON serialization and every original field. Do not change the shared command/source fingerprint algorithm or prior encrypted purpose tags.
