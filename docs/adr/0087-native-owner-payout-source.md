# 0087 — Native owner payout source

F-FIN-07/20/21/22 require an owner payout to retain its beneficiary, funding location, effective terms, approvals and lifecycle independently of the immutable payment journal. One tenant-scoped `owner_payout` row stores that source. Balances remain derived from the existing postings. The original request identity is a normalized, tenant-unique UUID; creation and reads require both caller and current stored financial authority, with an independent funding-account grant. DTOs omit company bank metadata and encrypted beneficiary details.

The existing approval request and stage tables provide the approval chain. A nullable payout link identifies the source without creating a second approval engine. The existing stage insertion guard accepts a submitted payout while retaining its expense checks. Payout guards require immutable submitted terms, ordered transitions, matching stage/recipient snapshots and attributed audits. A paid payout must link one exact ownership debit and funding credit; its cancellation requires the existing journal reversal mechanism and an atomic source transition. These controls reuse `Money`, `authorize`, `present`, the audit writer and the tenant transaction boundary.

Migration 68 adds the source, indexes, tenant foreign keys and guards. It does not rewrite existing financial or approval rows. The connected upgrade proof compares all original financial, expense, approval and payout-method columns and PostgreSQL tuple versions before and after the physical database clone upgrade. Draft/read persistence is verified independently; native submission, scheduling, payment, reconciliation and complete acceptance remain unfinished in the existing feature tracker.
