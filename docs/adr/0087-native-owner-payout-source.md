# 0087 — Native owner payout source

F-FIN-07/20/21/22 require an owner payout to retain its beneficiary, funding location, effective terms, approvals and lifecycle independently of the immutable payment journal. One tenant-scoped `owner_payout` row stores that source. Balances remain derived from the existing postings. The original request identity is a normalized, tenant-unique UUID; creation and reads require both caller and current stored financial authority, with an independent funding-account grant. DTOs omit company bank metadata and encrypted beneficiary details.

The existing approval request and stage tables provide the approval chain. A nullable payout link identifies the source without creating a second approval engine. The existing stage insertion guard accepts a submitted payout while retaining its expense checks. Payout guards require immutable submitted terms, ordered transitions, matching stage/recipient snapshots and attributed audits. A paid payout must link one exact ownership debit and funding credit; its cancellation requires the existing journal reversal mechanism and an atomic source transition. These controls reuse `Money`, `authorize`, `present`, the audit writer and the tenant transaction boundary.

Migration 68 adds the source, indexes, tenant foreign keys and guards. It does not rewrite existing financial or approval rows. The connected upgrade proof compares all original financial, expense, approval and payout-method columns and PostgreSQL tuple versions before and after the physical database clone upgrade. Draft/read persistence is verified independently; native submission, scheduling, payment, reconciliation and complete acceptance remain unfinished in the existing feature tracker.

Configured rates use the existing `Money.multiply` with precision sized to the operands in a local Decimal clone. This prevents a reproduced one-cent loss on a legal portfolio balance and preserves global Decimal settings for concurrent requests. An independent integer basis-point oracle checks both signs and 500-property balances before the existing two-decimal rounding contract.

Payout timing uses one calendar planner for previews and native submission. Weekly, monthly, anchored fifteen-day and custom cron schedules require configured local times and calendar fields; no business schedule is supplied in code. Event holds use calendar days in the source timezone. `cron-parser` evaluates cron and the already installed `temporal-polyfill` handles civil dates, with the existing current-IANA-data guard. A civil clock label identifies a scheduled occurrence across repeated DST offsets. Agreement overrides use the existing condition evaluator and can change only the payout policy fields. Financial and approval terms remain frozen at submission; calendar planning alone does not execute a transfer.

Submission resolves current effective agreement rules for periodic payouts and retains the original owner commission/booking policy for booking-linked payouts. Missing source or reference evidence denies submission. Owner capacity comes from the shared statement engine, less approved/scheduled source commitments and the frozen holdback. One owner/property/currency lock serializes automatic and final reviewer approval. The shared approval request, stages, inbox and delivery checks serve both expenses and payouts; an operational grant cannot review a financial payout. Approval never creates payment postings.

Migration 69 adds an attributed expected-settlement instant for OTA payout planning. It is nullable for existing sources, audited on creation or draft change and immutable after submission. Its frozen snapshot must match the source. The connected 68-to-69 upgrade proof includes a populated migration-68 payout and preserves all original columns, tuple versions and migration metadata. Existing migration 68 remains unchanged. Native scheduling, payment, reversal, jobs and UI acceptance remain separate unfinished gates.

Per-booking payout timing requires the existing reservation transition from financial reconciliation to closed, with the reservation still closed. Its append-only revision ID, reservation version and database timestamp are frozen with the payout policy. The configured hold starts at that recorded completion instant. A planned checkout, request clock or status-only imported row cannot establish completion. This reuses the reservation lifecycle without rewriting booking history or changing the separate after-checkout cadence.
