# 0086 — Derived owner ledger

F-FIN-18/42 and handbook G.5 require opening plus credits minus debits to equal closing, grouped by the existing owner-payable buckets. The existing owner-statement generator and posting reader are shared in the ledger layer, with compatibility exports/delegates for existing owner-portal callers. Finance adds its authorized administrator view without a second calculation engine, balance table or migration. Money addition/subtraction uses exact minor-unit arithmetic to retain cents when 500 valid source amounts exceed an individual Decimal operation's precision; other Money contracts remain unchanged.

Each response builds aggregates, buckets and movements from one PostgreSQL Repeatable Read snapshot through that shared generator. A posting-ID cursor locates the page within the already scoped and database-ordered dataset. Stable order retains microsecond distinctions without converting cursor timestamps through JavaScript. The source date range uses explicit/configured timezone boundaries and PostgreSQL time. Archived financial history remains visible to currently authorized readers. The existing generator continues to reject unrecognized ledger buckets; no new business classification is introduced.

Complete totals require an unconditional `owner_statement:view` grant for the entire selected owner or property scope, independently in the caller context and current stored authority. Conditional movement visibility cannot be used to assemble a misleading partial balance. The existing `authorize` evaluator remains authoritative; contexts used for this additional aggregate check rebuild permission/scope unions from eligible assignments so an empty filtered set cannot fall back to discarded grants. Property-only grants require an explicit property filter. A selected property must belong to the owner's relationship history or existing owner-claim movements before its name is exposed.

A live whole-owner aggregate has no financial-record ID. Its authorization resource carries typed owner/property scope, so a grant to one journal cannot become portfolio access when IDs in different entity tables happen to coincide. The PostgreSQL regression uses valid journal and owner rows with the same UUID to prove this boundary.

Financial DTOs include the owner claim and safe movement provenance, with the existing `present` policies. Bank/location metadata, other owners and employee compensation are absent. Viewing a ledger writes an attributed audit; financial headers and postings remain unchanged. This live reader supplies statement data. Immutable PDF/export generation and its complete dataset hash remain separate required acceptance under the existing document/statement features, and no feature is marked DONE by this increment alone.
