# ADR 0130 — Shared hourly admission and financial source validation

Hourly creation admits a nonfinancial earning request before the existing shared worker writes a compensation run. Requests retain the reviewed amount, original work and approval, every original interval/contract/configuration reference, the explicit earning policy, and the actor's authorization cap. Admission does not create an earning run, claim, journal or movement. Exact retries and recovery remain bound to the actor and original intent.

Use a reusable earning-request header and outcome, with typed hourly work and contract-witness children. Source and witness validation is shared with hourly financial runs. PostgreSQL validation may project actual request fields into common validation records; it never inserts a placeholder financial row. A security-invoker view joins the two actual witness stores for common coverage, effective-rate and exact Money checks. Underlying tables retain forced tenant policies. The existing financial worker handles the new event without adding a function slot or changing its concurrency or retry settings.

Original assignment identity is protected once a request retains its contractual witnesses, while retirement and login changes remain possible. Receipt and audit readers derive every scope and original rate from actual foreign keys. Stored JSON and captured authorization never grant access without fresh authorization. Execution rechecks the original reviewed source fingerprint; changed work, policies, rates or authority produce a terminal conflict or denial while retaining the original request and audit history.

Creation nonces share the existing compensation-run lock across monthly and actual-work requests. Neither mode can take the other's pending or terminal intent, and a financial run must preserve the original pending request's actor, mode, fingerprint and calendar. The existing worker-reference guard protects both event types while permitting delivery metadata changes. Full source validation runs at request birth; child guards retain the same-birth and immutable-slot checks, including an attempted append after an earlier constraint flush, without rescanning every source for each inserted child.

The actual 500-property admission profile exposed repeated JSON-to-row conversion inside the common SQL validator. PostgreSQL expands a composite function's `.*` output by calling the function for each selected column. Use the unchanged conversion expression as a lateral FROM item so each actual source and header is converted once. All source, tenant, Money, coverage, history and audit predicates remain identical. Migration 111 contains only those two query rewrites; earlier applied SQL remains frozen. Rollback qualification repeats all 81 adverse cases under a NOBYPASS role and checks every original row and xmin. The same complete 500-source guard fell from 7.83 seconds to 1.10 seconds in the rollback profile; authenticated admission is measured separately.

Migration 112 converts the exact header fields consumed by the shared row type, preserving the original created-by/time mappings while excluding discarded intent and authorization JSON. Every projected value matches all 65 actual headers in the qualification fixture, and all 81 adverse cases still pass. The complete guard then took 0.73 seconds. Twenty new authenticated 500-property admissions measured p95 1,886 ms and maximum 1,889 ms, with exact retries/recovery and no financial rows during admission. Both populated forward upgrades preserve every prior business value and xmin; neither change modifies an applied migration or a validation predicate.
