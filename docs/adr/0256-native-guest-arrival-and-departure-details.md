# ADR0256: Native guest arrival and departure details

Guest-reported property arrival and departure are reservation-scoped plans. They append their own encrypted native history and never silently change canonical booking dates, operational check-in/out, tasks, prices or financial identity. Travel methods and references are separate approved fields; collecting a plan does not create a transfer or other service order.

Access requires a separate explicit signed STAY_DETAILS grant on the original stay capability. The existing tenant/source-bound form-grant journal, capability gateway, personal source authorization, purpose-separated private key ring, audit and outbox infrastructure are reused. Profile grants retain their original scope and signed bytes. Applied migrations and all previous native/financial histories remain intact through forward migrations.

An enabled form requires explicit processing approval, owner-supplied EN/FR notice content with optional AR, field/required choices, allowed travel methods, arrival/departure day windows and request budgets in config_rule. There are no business window, method, notice or consent defaults. Captured/current fields, methods and windows intersect. Changed purpose or notice requires a fresh grant; withdrawals never expose previously excluded data.

Guests provide property-local clock values. The server resolves them using the existing current-IANA helpers and the actual native property timezone. Missing clock times are rejected; repeated clock times require an explicit occurrence. Review authenticates the current source, policy, normalized local values and resolved instants before immutable admission. Original revisions retain their captured timezone and instants for recovery under key rotation. Field validation returns only bounded issue codes after current form authority is established.

The EN/FR/AR flow must retain original UUIDs through lost or unrecorded replies, keep private travel values out of browser persistence/logs/audit payloads, and clear private state on withdrawal/offline/hidden pages. Native database, isolation, concurrency, source/financial preservation, original-profile compatibility, backup/restore and production desktop/mobile gates precede qualification. F-GST-04 remains IN-PROGRESS through incomplete acceptance and restricted hosted staging. All355 approved features remain required.

Staff form decisions share one review/admission/recovery manager with explicit per-form paths, namespaces and nonce keys. Original profile routes, signed serialization, messages and storage keys remain compatible. Public availability reads a bounded set of actual latest form heads and rechecks both forms against the final native source; it never infers readiness from a read link. Guest clocks and travel choices come only from the current approved form policy. Field errors retain only bounded codes after authority fences, while denial, offline and hidden pages clear private form state.

The browser response limit is256KiB so the existing closed notice can retain all30 paragraphs, all three languages and the full240-character localized-text limit, including JSON-escaped Unicode/control characters. This is a bounded transport allowance, not a processing or business-rule default. Native tests prove unchanged booking/tasks/financial history; compatibility tests recover original244 capabilities/revocation and246 grants/profile commands on the forward248 copy without repeating preparation or backup/restore.
