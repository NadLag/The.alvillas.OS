# 0041 — Staff assignments and lifecycle

Team Management extends the existing Person, UserAccount and RoleAssignment records. A person can work without an account. Account-backed assignments use that person's active account and the existing permission grant checks. Scoped readers receive only matching assignments; a staff account receives a capability to read its own operational profile. Financial and document access require separate permissions.

An expiry notification carries the document reference separately from the person used for document authorization. Destination resolution validates both references before returning the staff profile link. Archival removes the target from reminder navigation.

Inviting a login for an existing staff member requires explicit profile selection and identity view, create and edit grants on that person. The invitation uses the saved contacts and locale, preserves the person reference, and checks scoped role administration and permission grant ceilings. Contact matching never implicitly selects or rewrites a profile. Activation locks the person, requires an active profile without an account and unchanged contacts, creates a new account and revokes other pending invitations. Existing account credentials cannot be replaced by accepting an invitation.

The audit serializer applies those same grants to private payloads and reasons. Audit access and general financial access alone do not reveal staff compensation, documents or personal contacts. Leave and offboarding reasons require personal-record access. Assignment audit details require scoped role administration.

Compensation belongs to an assignment. Each change creates a `staff.compensation` config_rule version scoped to that assignment and an immutable, tenant-bound version reference. Effective instants must increase; concurrent changes use a person lock and an expected version. Earlier rates remain queryable. Salary, job, hourly and percentage values retain decimal precision and currency.

Availability uses calendar dates with an exclusive return date. Approval and task assignment share database locks. Approved absences cannot overlap other approved intervals or open work. Task assignment also checks absences, archived staff and account status, including writes through other operational entry points.

A staff wallet links one dedicated STAFF_WALLET custody account to one person. Administrators can create that account through the existing finance repository or link an existing dedicated account; bank and ownership accounts cannot be linked. Its per-currency balances and movements come from the financial ledger. This records cash location without transferring money ownership. Linking and creation require financial authorization. Offboarding and assignment retirement retain all business history and require clear tasks and wallets. Database triggers protect account deactivation, task assignment and subsequent wallet postings from concurrent bypasses.

Staff documents use the existing private R2 provider and versioned encryption key ring. Uploads validate ownership, size, declared type and file signature before AES-256-GCM encryption. Authenticated additional data binds each encrypted object to its tenant, person, storage key, content type and plaintext size. Ciphertext alone reaches R2; object keys and signed storage URLs are never serialized to the interface. Each download authorizes the current session, retrieves the encrypted object using an internal short-lived signature, authenticates and decrypts it on the server, then returns a non-cacheable attachment. Failed integrity checks return no document. Retain previous encryption key versions for existing files. Archiving blocks future downloads immediately and retains encrypted business history. File limits, internal signature duration and reminder thresholds live in config_rule; the four-million-byte technical ceiling keeps the multipart request within the hosting payload limit. Reminder delivery reuses the existing configurable notification routing, recipient authorization, preferences and idempotent outbox. No default administrative or operational recipient is inferred. Storage retention and legal employment policy remain owner decisions.
