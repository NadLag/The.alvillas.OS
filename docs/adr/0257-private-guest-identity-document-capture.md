# Private Guest Hub identity document capture

F-GST-05 uses the existing encrypted document archive. It does not establish a legal basis for collecting identity documents. Collection requires an explicitly enabled, scoped `guest_hub.identity_documents` rule with processing and retention approval references, an approved multilingual notice, document type mappings, allowed and required sides, retention tags, byte and capture limits, and independent admission and upload budgets. No approval, legal wording, document requirement or retention period is seeded as a production default.

An original signed form grant intersects the captured and current policies. Later rules can narrow collection. They cannot add document kinds, sides or content types to an existing grant, increase its limits, change its canonical document type, or repurpose its processing notice or retention decision. Changed purposes and retention mappings require a fresh grant. Newly required kinds or sides that were never granted close the existing collection path.

Canonical document versions remain the source of encrypted files and their retention metadata. Native capture records will bind those versions to the actual organization, reservation, guest, private link, signed form grant and captured policy. Guest collection must use the existing tenant, authorization, capability, audit, outbox and document storage boundaries. Original file names, identity numbers, extracted document text and public storage URLs are not part of the collection contract. Browser recovery retains scoped random command identifiers; file bytes remain transient. Collection does not modify operational check-in or financial identity.

Document creation requires independently delegated document authority. A separate purpose-bound signature binds the original form-grant fingerprint, actual tenant and creator, captured authorization restriction, and canonical archive and retention policies. Current stored document authority must continue to intersect that captured restriction. The additional delegation must be retained alongside the native identity grant; existing PROFILE and STAY_DETAILS grant bytes and their signing purpose stay unchanged.

An identity-only grant extension records that delegation in the same transaction as the native grant, metadata audit and outbox event. The original document source requires its own property and reservation access, sensitive document view/create, and retention-edit authority. Public collection also rechecks the original grantor's captured and current Guest Hub, personal guest and document permissions. Withdrawing processing or a permission closes collection; recovery of a recorded grant remains metadata and does not require a private key or renewed collection authority.

Database birth checks use the stored grant's explicitly selected system transaction marker. A copied PostgreSQL table-row composite does not retain that tuple header. Migration250 selects the actual `g.xmin` beside its user columns and retains every source, policy, timing and atomic-delegation predicate; applied migration249 remains unchanged. An identity grant cannot commit when its document delegation write is omitted.

Capture review, command commitments and encrypted descriptors reuse the existing private-form codec with separate identity-document purposes. The review binds the original nonce, predecessor, grant, effective form, source and exact filename-free descriptors. AEAD also binds the server-assigned file identities and sides through an immutable manifest fingerprint. Plain document hashes and chunk hashes stay inside the encrypted payload. Retained key rotation preserves original recoverability; profile, stay-details and delegation signatures cannot authorize a capture.

Capture admission atomically persists an encrypted intent, immutable file identities, a metadata-only audit with a null human actor, and an original outbox event. Native birth guards require the live original identity grant, actual source and approved policy, the exact reservation/guest predecessor, and every file in the closed manifest in the same transaction. The configured capture limit follows that reservation and guest across links. Omitted file writes roll back the capture, event and audit. Recovery uses the original nonce and grant; changed commands or replacement grants cannot inherit the original intent. This receipt acknowledges persisted descriptors only. Canonical encrypted file publication and atomic retention acknowledgements are separate required steps.

The existing capability boundary also supplies an ephemeral request lease for canonical document transactions. Verification, read and configured upload budgets are charged at construction; repeated transaction checks within that request do not create another public admission path. Each phase rechecks the actual original capture/file, current signed grant, original grantor cap, independent canonical document and retention authority, approved descriptors and latest capture. Source or form changes during I/O close that request. A fresh request may retain a valid original descriptor under narrower current constraints. Final fences run after the caller's proposed writes so authority withdrawal rolls back publication metadata. Object I/O occurs between transactions, with no outer Guest Hub transaction holding locks. Tokens and file bytes are never persisted in the lease.

Legal approval, retention and disposition decisions, real provider enablement, restricted hosted acceptance and production changes remain owner-reserved. This decision supplies no automatic document-disposition workflow.
