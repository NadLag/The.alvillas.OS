# ADR 0039: Durable notification delivery diagnostics

F-NTF-08 extends `notification_delivery`, the existing outbox, Resend, signed Inngest execution, authorization, presentation and audit. Email, identity invitations/recovery, digests and browser push share a tenant-scoped administrator view. Viewing requires organization-scoped audit viewing and configuration access; retrying additionally requires audit edit permission. Recipient addresses, payloads and provider identifiers never enter the administrator response.

Completed attempts and verified provider events are append-only `notification_delivery_log` rows with composite tenant foreign keys, forced RLS and indexed cursor pagination. Existing deliveries retain their real summaries; no historical attempts are invented. Invitation deliveries may precede account creation, so email delivery permits a null account reference while validating the actual tenant invitation and person before sending.

Email requests are encrypted and committed before contacting Resend. Retries preserve the exact content, sender and existing provider idempotency key. Config rules bound attempts, exponential delay and a window strictly shorter than Resend's 24-hour retention. Retry-After is a lower bound. Conflicting idempotent payloads, authentication errors and other permanent request failures terminate. Manual actions only queue an eligible outbox entry; they cannot reset counts, bypass cooldowns, revive terminal deliveries or extend the safe window. The signed worker rechecks current recipient, access and consent. Previously attempted legacy events outside the safe window are stopped.

The existing Svix verifier checks the raw body, timestamp and signature. Persisted events strip recipients, subjects, SMTP diagnostics and arbitrary provider messages. A matched provider email identifier and tenant delivery tag are required. Unique receipt keys and delivery locks make duplicates harmless. Late hard bounces and complaints take precedence over delivery; delayed receipts leave retrying to Resend. Terminal bounces never cause another send. Hard bounces, complaints and provider suppressions create tenant/address suppression fingerprints, also checked by identity and digest senders. Changed addresses have different fingerprints. There is no automatic removal or operator override of suppressions.

The migration expands notification infrastructure only and preserves existing records and financial data. It runs locally and on staging, with a verified backup before staging migration. Production promotion remains separate.

Provider contracts: [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys), [official test recipients](https://resend.com/docs/dashboard/emails/send-test-emails), [Resend webhook reference](https://github.com/resend/resend-skills/blob/main/skills/resend/references/webhooks.md).
