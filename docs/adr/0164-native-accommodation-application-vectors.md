# 0164 — Native vectors for partial accommodation applications

An application consumes actual held guest funds. A booking quote supplies a limit and source evidence; it does not create an unfunded owner payable. Recognition eligibility and original owner/rule snapshots remain responsibilities of the native financial source workflow.

Reuse the reservation engine's existing owner allocations, commission calculations and posting builders. Compute the difference between its canonical targets before and after an application. This preserves the original engine's exact result across partial amounts, including the commission cent that independently rounded small applications could otherwise lose. The difference helper selects no owner, rate, recognition event or accounting policy.

Keys retain account, currency, bucket and complete native dimensions, with JSON key order ignored. Differences use only `Money` arithmetic. Negative differences become positive postings on the opposite side; zero differences create no posting. This also represents native co-owner cent reallocations without changing earlier rows. Exact original opposites and any necessary subsequent ownership adjustment remain separate immutable financial events. No synthetic target or balance is persisted.

Funded application requires an explicitly selected policy for actual checkout and current open-period posting. The original checkout period must also remain open for first recognition, and the original commission snapshots must select checkout accrual. The source carries the real confirmation, checkout revision, financial snapshot, original owner order and retained native targets. Security deposits retain their refund-only treatment.

Additive SQL guards independently validate the original source, same-transaction audit, source-fund and quote caps, canonical per-command difference, complete cumulative ownership vector and retained audit targets. Bank and original-cash guards retain their existing implementations. The command serializes with refunds and other booking financial corrections through the existing booking, account, calendar, policy and original-source locks. No second receipt, physical cash movement or payment event is produced by ownership application.

An earlier partial correction records the exact original opposite first and attributes any necessary ownership-only allocation journal to that opposite. The native target for the remaining applied amount determines this adjustment, including co-owner and commission cent reallocations. Both journals use the existing batch writer: all actual headers are created before any posting, and posting resolution can reference those actual header identities. Existing array-based callers retain their interface. Separate guards bind both audits, exact original postings, retained targets and the adjustment's actual parent; no principal or physical location is added by allocation correction.

Application, opposite and adjustment postings must independently match the currency catalog's minor unit. An unrepresentable native commission or allocation is rejected as an explicit configuration issue; a different rounding or recognition policy is never substituted. Nonce-only recovery intersects original caller restrictions and current financial visibility for each retained owner source, including after payment authority ends.

Reservation-level financial refunds compose the same canonical application corrections within the existing tenant transaction. An aggregate audit retains the original request and actual child nonces for replay. Advancing a reservation to reconciliation or closure does not replace the original financial snapshot used by its application. The reservation caller repeats the canonical correction checks after its final audit and source writes; expired payment authority rolls back both the financial correction and the reservation revision. Restored guest ownership remains available to the explicit source-scoped physical refund workflow.
