# Native onboarding materializes canonical automation

Native workflow configuration must become executable through the existing automation/configuration services. A catalog or an accepted activation request alone does not prove that runtime workflows exist.

The compiler consumes the approved operational catalog and requires its actual localized name, enabled state, condition, canonical actions and retry settings. Missing or legacy incomplete execution fields block materialization. It selects no retry, schedule, action, enabled or naming defaults. Existing catalog extensions remain in their original encrypted source.

Each property/workflow identity receives a stable bounded canonical key. The materializer restores the actual activation creator cap, checks current approval/configuration/source authority, reads the exact selected catalog metadata before values and writes all definitions through the canonical automation service in one tenant transaction. A shared property lock serializes workers. Current and captured destination permissions precede private destination values. Existing inactive, retired, future or changed definitions are preserved as conflicts. Exact current approved definitions are reused without new versions or audit/outbox writes.

Canonical automation owns actual runtime events, authorization, configured retries, task generation and diagnostics. This adapter neither executes actions nor appends successful native phases or changes Property status. The dependency-ordered activation producer, actual Tasks/Notification receipts and operational transition guards remain required.

Tests prepare explicit execution configuration, recapture canonical Review after property-scoped grant setup, and exercise actual configuration writes, rollback, concurrency, retirement, held/current authority and native reservation/task services. Fixture preparation never relaxes the production source-change guard.
