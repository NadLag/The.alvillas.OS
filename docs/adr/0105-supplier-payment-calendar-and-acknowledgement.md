# Supplier payment calendars and interrupted acknowledgements

Supplier payment controls use the existing settlement reader, payment writer and exact reversal writer. The reader exposes only presented, tenant-restricted claim, payment and funding details. Original caller restrictions and current stored grants independently protect source costs, whole-invoice caps, original paid dates, posting dates, physical accounts and wallets. Funding choices are searched and paginated, and their financial view authority is checked again before returning names. Each reversal availability hint uses the writer's original-paid, posting and current-date checks; actual mutations always authorize again.

Local payment dates use the configured accounting calendar and the shared `localClockInstant` implementation with current IANA data. A nonexistent clock is rejected; a repeated clock requires an explicit occurrence. A reviewed form carries its canonical instant and calendar version. Before a new payment, the writer takes the shared accounting-period lock followed by the config-version lock, then compares the current rule and local conversion. This uses the same lock order as period close. An existing payment replays its original canonical intent before this form-calendar check, so changing a timezone cannot reinterpret or duplicate an already recorded payment.

A default current-clock preview starts from a known server instant. The shared local-clock helper retains that instant's actual occurrence, including a half-hour fallback, and the panel initializes its occurrence selector from the authorized server preview. This prevents an ordinary claim read from failing during the repeated hour. Operator-entered ambiguous clocks still require an explicit occurrence; nonexistent clocks remain rejected. The reviewed command still carries that occurrence and the unchanged calendar-version binding. Both actual fallback occurrences are covered with real PostgreSQL claim reads, unchanged financial movements and explicit-input rejection checks.

An interrupted mutation response freezes the full original payment and nonce, or the exact original reversal reason. Confirmation retries that same intent. Unknown server failures are treated as uncertain because a post-commit response can fail. An acknowledged success refreshes the derived statement; a denied response clears private payment details. Offline controls cannot enqueue financial writes. Closed paid periods require explicit current-period consent and override authority; all journal and audit provenance remains in the existing append-only source receipts.

The panel is mounted only inside an independently authorized recognized-invoice view. All product strings use EN, FR and AR message files and existing design-system controls. This decision introduces no schema migration, payment-provider call or editable balance.

The shared source fence rejects city or region metadata changing during an operation. A real property-city change while a payment waited on its funding lock reproduced stale captured payment scope; the fresh source comparison now rolls back that write. All permission, amount and date assertions remain intact.
