# 0198 — Native signature drafts and explicit provider effects

F-DOC-06. Scope unchanged: all 355 approved features remain required.

Reuse `Signature`, `SignatureRecipient`, `SignatureEvent`, the private document archive, authorization caps, exact generation lineage, audit writer and outbox. A draft names one actual generated instance and its archived PDF version. Recipients name existing Person, Owner, Guest or Supplier records; public commands cannot supply contacts, tenant claims, financial values or authority. Current and held source, template, financial, signature and independent counterparty permissions remain necessary. Contact export uses the existing field presenter. Reviewed source changes require another explicit review.

Commit the original command, policy, authorization restriction, PDF digest and reference, recipient fingerprints, identity-bound encrypted contact snapshots, DRAFT evidence, private document history, canonical audit and reference-only outbox atomically before provider I/O. Upload, generation and signature commands share the actor/nonce lock; another protocol cannot reuse that nonce. Recovery returns that actor's original request. Later business amendments cannot substitute their PDF under an earlier signature. Canonical audit and events carry references and counts, never contact details or legal clauses. The browser retains only its scoped random recovery nonce; private metadata stays in memory and is discarded on visibility, account, focus and offline boundaries.

Migration194 adds one nonce lookup index and native protocol guards, without a new business table, business DML or backfill. Previous SQL and legacy signature protocols remain intact. Native draft guards reject non-DRAFT events until the durable provider and signed archive transition protocol is implemented. Retained financial rows, immutable document bodies and original tuple versions remain unchanged. A draft is a real saved request, with no asserted delivery or signed outcome.

Extend the existing `SignatureProvider` rather than introducing another adapter. Current Documenso v2 envelopes support distinct private preparation, observation and explicit distribution. The adapter validates the actual uploaded PDF bytes, parent identities, recipients, fields and receipt; it bounds responses, rejects redirects and sanitizes failures. A lost or malformed effectful acknowledgement remains UNCERTAIN and must not cause an automatic second request. The existing legacy API contract remains available for compatibility. Owned HTTP acceptance exercises the real transport; it does not claim an authenticated Documenso account acceptance.

Documenso webhooks authenticate the configured `X-Documenso-Secret` using constant-time comparison before decoding a bounded body. Missing configuration always denies access. Canonical event evidence excludes tokens and caller tenant claims; raw evidence must be encrypted before persistence. A recipient-signed event cannot establish full completion or the existence of an archived signed PDF. Signed return integration must preserve business effective-version ordering when an older instance is signed after a newer amendment.

Provider dispatch admission, uncertain-effect reconciliation, persistent authenticated webhook transitions, signed PDF and certificate return, expiry, legal signature level, owner-approved provider operation and hosted acceptance remain required. No legal approval, provider account operation, deployment, production migration or feature DONE status follows from local draft acceptance. The provider supports the application's EN and FR signing metadata; AR requires a verified provider capability and never silently falls back to another language.
