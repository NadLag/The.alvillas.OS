# 0183 — Configured native payment providers

Status: Accepted

F-FIN-08 supplies configured payment methods and provider adapters while the existing financial engine remains responsible for journals, custody and ownership. Method identities and EN/FR/AR labels are versioned lookup data in `config_rule` under `finance.payment_methods`. Technical adapter identities select cash, bank transfer, manual receipt, Airbnb settlement or PayPal protocols. Definitions require explicit enablement and registered supported currencies. Financial configuration and its history retain independent transaction, cash and bank source authorization.

Native cash, bank-transfer, manual and Airbnb adapters delegate monetary work to the original receipt or settlement services. Their known producers borrow one outer tenant transaction with the existing default limits; altered isolation or timeout requests fail closed. Funding accounts lock before method definitions. The final definition fence, method audit and original producer replay commit together, so a changed definition or revoked authority withholds the result and rolls back the new journal. The adapters preserve the caller's original capability and recheck native stored authority through the canonical producer.

An actor-bound source identity and command hash recover the original accepted payment without another journal or acceptance audit. Recovery uses the original method evidence even after the definition is disabled. Existing receipts admitted through an older path remain historical records; the new path does not retroactively attribute them to a later definition. Cash admission reclassifies existing claims while preserving the original custody movement.

The optional PayPal adapter validates original order identity, completed capture identity and exact Money before returning a receipt. Its existing single-payment interface fails closed on an ambiguous response. OAuth, transport and capture errors retain status codes without returning provider response bodies. A canonical intent supplies the external idempotency identity. PayPal describes the distinct capture identity and completion states in its [Orders purchase-unit reference](https://developer.paypal.com/api/orders/v2/definitions/purchase_unit), and the request identity in [Making API requests](https://developer.paypal.com/api/make-api-requests).

Controller integration must bind the method definition to the user's reviewed native command before enabling the new admission path. External capture must use a durable tenant- and actor-bound original intent and run outside financial transactions. The subsequent financial admission must retain the confirmed source and complete reservation, guest, property, owner, collector, account and purpose provenance through F-FIN-09. Provider confirmation never establishes an editable balance or infers ownership from custody.
