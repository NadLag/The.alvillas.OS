# 0084 — Posted expense amount corrections

F-FIN-05 and handbook G.3.12 require reasoned financial corrections that preserve posted history. A revised invoice is a separate native expense referencing the original expense and its observed version. The source link is immutable. Only the amount changes; currency, funding, category, invoice date, ownership and agreement versions remain tied to the original. A correction does not inherit an emergency approval waiver.

Preparing a draft requires original expense access, independent financial view and override, authorized funding and expense creation. The original stays posted while the replacement goes through the existing approval workflow. The existing policy evaluator recomputes the revised allocation and required approvals using frozen original evidence, including referenced configuration versions.

Posting acquires both expense locks in canonical order. It requires authority on both sources, explicit current-period intent and the replacement's completed approval. Existing void and posting commands share the same tenant transaction: an exact opposite journal and the approved replacement commit together. A reasoned financial audit links both invoices, the original journal, reversal and replacement. Current stored grants and supplied restrictions are checked after period waits with PostgreSQL time. A losing concurrent correction writes nothing; exact retries acknowledge the original actor, version, reason and mode.

Forward migration 65 adds nullable tenant-bound source fields without changing existing financial headers or posting values. Guards preserve source identity, require original agreement evidence and atomic linked audits, reject backdated replacement journals and retain the existing allocation, approval and exact-reversal checks. Corrections to already corrected invoices form a source chain; journals remain immutable. CI, upgrade preservation, authenticated native acceptance and staging are mandatory before completion.
