# 0157 — Periodic owner payout draft admission

Periodic proposals need a creation calendar distinct from payment eligibility. A missed worker tick must not make several competing claims on the same current owner payable. An approved payout must retain its original eligibility, recipient and approval evidence.

`finance.recurring_payout_drafts` explicitly selects the current configuration author, target owner/property/currency, native payout recipient and funding account, creation calendar, start instant and batch size. The worker considers only the latest due civil slot and waits while that owner/property/currency has an open native payout. Calendar calculation reuses the existing payout calendar and timezone guard, including anchored fifteen-day intervals and stable civil identities through repeated DST offsets. Previously issued target/slot pairs are fetched together before native source evaluation.

Amounts use the canonical owner ledger and configured payout planner: current payable after the selected holdback, less native commitments, calculated with `Money`. The actual resulting amount is checked again through the existing native payout policy, including conditional agreements, independent funding access, recipient validity and approval routing. Event-dependent payment policies still require their real reservation or settlement source. No booking, invoice, payment or settlement is invented for a periodic proposal.

The job creates a native DRAFT and an append-only, tenant-scoped occurrence in one transaction. A shared native owner lock serializes proposal creation with manual creation and payout transitions. Unique target/civil-slot and source-payout constraints make duplicate delivery harmless. Database admission requires the actual newly created unpaid draft, current authored configuration, configured target, due civil clock, native validation evidence and attributed atomic audit. Applied migration bytes remain unchanged; subsequent guard corrections use additive migrations.

The occurrence retains private policy and balance evidence. The general payout audit contains only source identifiers and the civil slot. Generic configuration and audit presentation require independent organization-wide financial-transaction and owner-statement access; exports require both source export grants. Held restrictions and current stored grants apply, with final checks over every generated source before commit.

Human submission recalculates and freezes the actual native payout policy. Approval, scheduling of approved sources, actual payment, reversals and accounting-period checks retain their existing workflows. This child change depends on the owner-payout stack; its release and authenticated staging acceptance remain subject to that stack's existing gates.
