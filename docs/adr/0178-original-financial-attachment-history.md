# 0178 — Original financial attachment history

Receipt and invoice files belong to an existing sealed journal, with composite organization foreign keys. Attaching or correcting a file never changes a journal, posting, balance, settlement or accounting period. A correction appends a version to one logical file; the previous version and original bytes remain downloadable. PostgreSQL enforces tenant isolation, immutable admissions and versions, a linear history, and attributed audit records in the same transaction as each admission and completed attachment.

Document authority is independent of operational access and financial journal authority. Both held and currently stored grants must permit the original native financial sources and the document action. Native employee claims, contractual salary sources, funding wallets, supplier invoices and retained company classification links remain protected. Mixed property journals require complete organization authority; different currencies are never combined into a fabricated permission amount. The audit viewer and CSV use the same source projections and serializer masking. Listing is bounded, and completed metadata contains no storage credentials or signed object URLs.

An explicit `finance.transaction_attachments` rule supplies allowed content types, byte limits, intent lifetime, storage read lifetime and actor admission limits. Admission and rate consumption commit before transport. The server independently verifies exact byte length, SHA-256 and declared file framing. Framing checks establish the supported envelope; they do not assert malware scanning or complete document decoding. Downloads use attachment disposition, sandboxing, no-sniff and private no-store responses.

The existing versioned AES-GCM byte encryption authenticates organization, journal, file ID, MIME type, length and plaintext hash. Persistent financial files require explicit `ENCRYPTION_KEYS`; they cannot rely on an authentication-secret fallback. Retained key versions are required to read historical files. R2 stores an encrypted, opaque object with conditional creation. After a lost acknowledgement, a repeated command verifies the retained ciphertext and original plaintext rather than replacing the object. HTTP and browser operations have no automatic retries.

Object I/O runs outside database transactions. Before metadata commits or plaintext leaves the service, the application recaptures the current policy, original source facts and authority and commits the attributed audit. A failed fence leaves a private encrypted orphan and its durable admission budget; it does not invent a successful attachment or delete evidence. The client retains an in-memory command for an explicit resume, and clears private metadata and selected files on denial or loss of connectivity. It does not cache financial documents for offline use.
