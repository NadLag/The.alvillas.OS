# ADR0255: Explicit Guest Hub profile grants and native profile history

A stay link's existing read authority never becomes profile authority automatically. Staff must explicitly grant or withdraw profile access through an append-only, source-bound grant journal. Grant admission requires independent held/current authority over the link, reservation and canonical guest, including personal guest viewing/editing. Each grant is signed with the existing purpose-separated private key ring and binds the exact original link hash, tenant, stay, property, guest, policy, source, predecessor and command. A withdrawal closes profile access while retaining the original link and all history.

Profile collection requires explicit configured field/requirement choices, request budgets, processing approval and owner-supplied EN/FR notice content with optional AR. There is no legal notice, country, enabled form or consent default. Captured and current rights intersect; changes to processing purpose or notice require a new explicit grant. Technical contact normalization reuses the existing international-phone helper. Government ID/passport collection remains a separate approved feature and owner-reserved privacy decision.

Guest submissions create encrypted, append-only revisions scoped to one reservation and canonical guest. They do not silently overwrite the shared guest record, another stay or financial identity/history. Authorized views reuse canonical source contact data and the latest permitted native revision; an explicit null never falls back to an older contact value. Review and command commitments use private, purpose-bound MACs instead of public hashes of guessable personal data. Private payloads bind the full immutable revision header through the existing AEAD helper and clear temporary plaintext buffers.

Admission, source lineage, outbox and metadata-only audit commit atomically. Every guest read/write rechecks the original link, actual source, current grant/policy, database clock, budgets and final withdrawal/revocation. Lost replies recover the original UUID command; browser storage retains only its scoped UUID. Form data stays out of logs, audit payloads and browser persistence. The EN/FR/AR flow must exercise native database, authorization, acknowledgement-loss, offline/private clearing, keyboard/360px and financial-preservation gates before qualification.

All355 approved features remain required. Legal/provider enablement, restricted hosted staging, production promotion and billing remain owner-reserved gates before DONE.
